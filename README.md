## Что изменилось в v80

- Удалён активный модуль `js/core/sync-merge.js` и вся очередь `kiri:rp-cabinet:v79:mutation-queue`.
- Создан новый канонический документ Firebase `default_realtime`.
- Панель включает постоянный `onSnapshot` и получает изменения с телефона, ПК и других вкладок сразу после записи Firestore.
- Галочки записываются по отдельным вложенным Firestore-путям. Вторая галочка не отправляет весь список и не может снять первую.
- Имя, тема, организация, раздел, ступень, закрепления, калькулятор премии, доказательства и отчёты также записываются точечно, а не целым локальным снимком.
- При открытии и обновлении страницы выполняется только серверное чтение `get({source: 'server'})`; локальный кэш не создаёт запись.
- Закрытое устройство при открытии ждёт серверный снимок. Кэш может быть показан только как офлайн-резерв и никогда не отправляется назад автоматически.
- Включено нативное IndexedDB-хранилище Firestore с `synchronizeTabs: true`, чтобы несколько вкладок одного устройства использовали одну очередь SDK.
- Удалены старые локальные очереди v77–v79 при запуске v80.
- Статус «Синхронизация активна» показывается только после получения серверного снимка Firebase.
- Сохранены неограниченные загрузки скриншотов из v78 и вся функциональность панели.

## Как синхронизация работает

1. Телефон и ПК входят в один Google-аккаунт.
2. Пользователь меняет конкретное поле или галочку.
3. Браузер отправляет `update()` только для соответствующего Firestore-пути.
4. Firestore сразу выдаёт обновлённый снимок всем открытым устройствам через `onSnapshot`.
5. Если устройство было закрыто, при открытии оно сначала читает серверный документ `default_realtime`.
6. Обновление страницы не вызывает облачную запись, поэтому старый кэш не может откатить другое устройство.
7. Одновременные изменения разных полей объединяются нативно Firestore. Для одной и той же галочки действует последнее подтверждённое сервером действие.
8. При временном отсутствии сети запись удерживается SDK Firestore; собственная очередь RP CABINET больше не используется.

## Как добавлять новые повышения

1. Добавить название ступени в массив нужного отдела в `data/levels.js`.
2. Добавить задания с абсолютно таким же названием ступени в `data/progress/<отдел>.js`.
3. Если создаётся новый файл отдела, подключить его в `index.html` после `data/progress/index.js`.
4. Не переименовывать уже опубликованные задания без необходимости: текст задания используется как стабильный ключ сохранённого прогресса.
5. Скриншоты назначаются централизованно в `data/progress/proof-rules.js`, а не внутри каждого списка.

## Синхронизация

Документ `users/{uid}/profiles/default_realtime` хранит профиль в нормализованной структуре: `core`, `progress`, `selectedLevels`, `pins`, `premium`, `account`, `proofs` и `reports`. Ключи контекстов и заданий кодируются так, чтобы каждая галочка имела собственный безопасный Firestore-путь.

Локально сохраняются только последний отображённый кэш и резервная копия. Они нужны для локального режима и временного офлайн-показа, но не участвуют в выборе победителя. При подключённом Google победителем всегда является последний серверный снимок Firebase.

`save()` сохраняет кэш и строит разницу только после реального пользовательского действия. Во время загрузки, входящего `onSnapshot`, авторизации и обновления страницы облачная запись заблокирована. Подробности находятся в `documentation/ARCHITECTURE.md`.
