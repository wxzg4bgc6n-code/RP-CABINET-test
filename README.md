# RP CABINET — TEST v79

Новая облачная синхронизация в реальном времени. Firebase является единственным источником истины после входа через Google. Открытие, обновление страницы или старый локальный кэш больше не могут перезаписать более свежие данные другого устройства.

## Что изменилось в v79

- Полностью удалена старая логика сравнения локального и облачного снимков по времени и «полноте».
- Создан новый канонический документ Firebase `default_v79_realtime`, изолированный от старых v77/v78-клиентов.
- При запуске с подключённым Google панель сначала читает Firebase и только потом показывает профиль.
- Локальный профиль является кэшем для быстрого/офлайн-доступа, но не отправляется в облако просто из-за открытия страницы.
- Каждое реальное действие пользователя хранится отдельной операцией: конкретная галочка, контекст, ступень, имя, тема, подтверждение или отчёт.
- Firestore-транзакция накладывает операцию на последнюю серверную версию и увеличивает `syncRevision`.
- Для каждой цели хранится серверная ревизия и идентификатор последней операции: повтор уже подтверждённого действия не применяется второй раз, а устаревшая операция закрытого устройства не может затереть более новое изменение той же галочки или настройки.
- Быстрые последовательные изменения одной цели внутри текущей вкладки связаны цепочкой `supersedesIds`, поэтому более поздний клик пользователя не отбрасывается из-за собственной предыдущей транзакции.
- `onSnapshot` постоянно слушает документ и сразу применяет новую ревизию на всех открытых устройствах, включая несколько вкладок одного устройства.
- Неотправленные офлайн-действия сохраняются в отдельной очереди v79 и накладываются поверх свежего облачного состояния после восстановления сети.
- Входящий снимок всегда показывается вместе с ещё не подтверждёнными локальными операциями, поэтому галочки не мигают и не откатываются.
- Старые локальные ключи v77 и облачный документ `default_v77` используются только один раз для миграции, если новый документ v79 ещё не создан.
- Cache-busting, видимый бейдж, `TEST_VERSION`, `TEST_VERSION_LABEL`, README и документация обновлены до v79.

## Как синхронизация должна работать

1. Телефон и ПК входят в один Google-аккаунт.
2. Изменение на телефоне записывается транзакцией в Firebase.
3. Открытый ПК получает следующую `syncRevision` через `onSnapshot` и сразу обновляет интерфейс.
4. То же работает в обратную сторону: ПК → Firebase → телефон.
5. Если телефон был закрыт, при следующем открытии сначала загружается последняя облачная ревизия, созданная на ПК.
6. Обновление страницы на старом устройстве не создаёт запись и не может откатить другое устройство.
7. Если сеть пропала после нажатия, операция остаётся в очереди и отправляется после восстановления соединения поверх последней серверной версии.
8. Если та же цель успела измениться в облаке после создания старой офлайн-операции, облачная версия сохраняется; несвязанные изменения продолжают объединяться.

- Снятая или поставленная галочка блокируется в интерфейсе до подтверждения сервером, поэтому старый снимок другого устройства не вызывает мигание.
- Две стартовые подсказки системы скриншотов объединены в одну рамку.
- Vercel проверяет Firebase ID token через официальный Identity Toolkit и больше не требует отсутствующий служебный ключ Firebase Admin.
- Для Vercel-проекта рекомендуется подключить папку `proof-service` из этого GitHub-репозитория, чтобы сервер обновлялся вместе с панелью.

## Как добавлять новые повышения

1. Добавить название ступени в массив нужного отдела в `data/levels.js`.
2. Добавить задания с абсолютно таким же названием ступени в `data/progress/<отдел>.js`.
3. Если создаётся новый файл отдела, подключить его в `index.html` после `data/progress/index.js`.
4. Не переименовывать уже опубликованные задания без необходимости: текст задания используется как стабильный ключ сохранённого прогресса.
5. Скриншоты назначаются централизованно в `data/progress/proof-rules.js`, а не внутри каждого списка.

## Синхронизация

Firebase-документ `default_v79_realtime` хранит канонический `state`, монотонную `syncRevision`, ревизии отдельных целей и короткий журнал обработанных идентификаторов операций. Устройства не сравнивают собственные часы и не решают, какой целый снимок «новее». Они отправляют только реальные операции пользователя, а транзакция применяет их к последней серверной версии с защитой от повторов и устаревших изменений одной цели.

Локально сохраняются:

- кэш последнего показанного профиля;
- резервная копия кэша;
- очередь ещё не подтверждённых пользовательских операций.

При открытии страницы локальный кэш не становится операцией. Если Google подключён, интерфейс ждёт чтения Firebase, применяет каноническое состояние и только затем показывает панель. Подробности находятся в `documentation/ARCHITECTURE.md`.
