# Архитектура RP Cabinet v79

## Главный принцип

ПК и телефон используют один `index.html`, общие данные и один облачный профиль. Мобильная версия меняет только раскладку через `css/responsive/mobile.css`; тексты, задания, тесты и изображения не дублируются.

## Где что менять

- `index.html` — структура главной страницы и порядок подключения файлов.
- `data/academy/` и `data/usaf/` — тексты и тесты отделов.
- `data/progress/` — задания повышения и правила подтверждений.
- `css/core.css` — основная геометрия.
- `css/features/` — оформление отдельных функций.
- `css/responsive/mobile.css` — только мобильная раскладка.
- `js/app.js` — профиль, прогресс, Firebase и запуск.
- `js/core/sync-merge.js` — очередь реальных пользовательских операций и их наложение на каноническое состояние Firebase.
- `js/features/progress-proofs.js` — очередь скриншотов и формирование отчёта.
- `report.html`, `js/report.js`, `css/report.css` — публичная страница одной ссылки.
- `proof-service/` — отдельный сервер Vercel и Vercel Blob.

## Прогресс

Прогресс и выбранная ступень хранятся отдельно для каждого сочетания:

`проект → путь → организация → раздел → ступень`.

Переключение Academy, MA, USAF, MP, DF, SD и ED восстанавливает свои галочки и свой выбранный ранг. Подтверждения скриншотами хранятся в `proofsByContext` по тому же ключу, поэтому файлы одного ранга не смешиваются с другим.

Ступени находятся в `data/levels.js`, а задания каждого отдела — в отдельном файле `data/progress/`. Название ступени в обоих местах должно совпадать полностью. Текст уже опубликованного задания без необходимости не меняется: он является ключом сохранённой галочки.

## Система скриншотов

1. Игрок отмечает пункт выполненным.
2. Отдельный блок ниже прогресса показывает название выполненного пункта.
3. Если доказательство нужно, рядом появляется загрузка скриншота.
4. Файл уходит напрямую из браузера в Vercel Blob. Base64 и само изображение в Firebase/localStorage не записываются.
5. В профиле хранится только короткая ссылка и технические размеры файла.
6. После выполнения всей ступени создаётся одна ссылка `report.html?id=...`.
7. Отчёт показывает каждый пункт и оригинальные изображения без обрезки.
8. Отчёт и связанные файлы удаляются автоматически через 8 дней либо вручную владельцем.

На один пункт отчёта можно загрузить любое количество оригинальных изображений; фиксированного лимита количества в панели нет.

Каким пунктам нужен скриншот, решает `data/progress/proof-rules.js`. Начиная с v71 изображение требуется только для участия в СО/специальной операции и ГМП. Остальные пункты остаются в общей ссылке как выполненные, но подтверждаются отметкой или тегом в Discord.

## Безопасный запуск профиля

При подключённом Google Firebase является единственным источником истины. Панель остаётся под `profile-booting`, пока не завершится проверка авторизации и чтение канонического документа `users/{uid}/profiles/default_v79_realtime`.

Порядок запуска:

1. `load()` читает локальный кэш, но не создаёт облачную операцию.
2. Firebase Auth определяет пользователя.
3. Если пользователь вошёл, `attachProfile()` сначала читает документ v79.
4. Если документ уже существует, его `state` применяется независимо от времени и полноты локального кэша.
5. Если документ v79 отсутствует, выполняется одноразовая миграция из `default_v77`, затем из `default`; локальный профиль используется только если старого облачного профиля нет.
6. Только после применения канонического состояния снимается `profile-booting` и показывается интерфейс.
7. Неотправленные операции, реально совершённые пользователем офлайн в v79, накладываются поверх канонического состояния и отправляются транзакцией.

Открытие, обновление страницы, восстановление контрольной точки и чтение локальной резервной копии не считаются пользовательскими действиями и не могут записать старый снимок поверх Firebase.

Локальные ключи v79 (`KEY`, `VERSION_KEY`, `PROFILE_BACKUP_KEY`) являются кэшем и резервной копией. Старые ключи v77 читаются только для миграции, если кэша v79 ещё нет. Старые клиенты v77/v78 используют другой облачный документ и не способны изменить `default_v79_realtime`.

Круг прогресса хранит фактически показанное промежуточное значение и текущую цель анимации. Повторный `render()` с той же целью не перезапускает переход, а новая цель продолжает движение с уже видимого процента.

Локальные CSS и JavaScript подключаются с маркером версии `?v=79`. Это обязательный cache bust для GitHub Pages.

## Дата регистрации

`account.createdAt` является неизменяемой датой создания профиля. При конфликте устройств выбирается самая ранняя корректная дата из основного профиля, старых локальных копий и даты первого входа пользователя в Firebase этого проекта. `lastSync` и обычный `updatedAt` не используются как дата регистрации.

## Синхронизация

Канонический документ содержит полный `state`, монотонную `syncRevision`, `targetRevisions`, `targetMutationIds` и ограниченный журнал `processedMutationIds`. Победителя определяют серверные Firestore-транзакции и причинная связь операций, а не часы телефона, `updatedAt` или оценка полноты локального снимка.

Каждое реальное изменение превращается в целевую операцию:

- `group` — имя, тема, карьерный контекст, закрепления или аккаунт;
- `task` — одна конкретная галочка одного контекста, включая явное `false` при снятии;
- `level` — выбранная ступень раздела;
- `proof` — подтверждения конкретного задания;
- `map` — отдельная запись отчёта.

Операции хранятся в `kiri:rp-cabinet:v79:mutation-queue`. Повторные операции для одной цели уплотняются до последнего значения и сохраняют цепочку `supersedesIds`. Firestore-транзакция читает свежий серверный документ, отбрасывает уже обработанные идентификаторы, не разрешает старой операции изменить цель, которая обновилась после её `baseRevision`, накладывает допустимые изменения, увеличивает `syncRevision` и записывает новый канонический `state`.

Если более позднее действие той же вкладки заменило ещё отправлявшуюся операцию, `supersedesIds` разрешает применить именно новый клик после подтверждения предыдущего. Поэтому защита от старого устройства не ломает быстрые последовательные нажатия пользователя.

`onSnapshot` работает постоянно и применяет каждую новую ревизию на ПК, телефоне и в других вкладках. Входящий снимок сначала объединяется с ещё не подтверждённой локальной очередью, поэтому интерфейс не откатывает галочки в ожидании завершения собственной транзакции.

Если устройство было закрыто, при следующем открытии оно не отправляет кэш: оно сначала получает последнюю ревизию Firebase. Если устройство было открыто без сети и пользователь совершал действия, после восстановления сети несвязанные операции применяются поверх свежего серверного состояния. Операция по цели, которая уже была изменена в более новой облачной ревизии, подтверждается как устаревшая и не откатывает облако.

## Версия панели

При создании новой версии обязательно одновременно менять:

1. `TEST_VERSION` и `TEST_VERSION_LABEL` в `js/core/version.js`;
2. `content` у `.kiri-test-version-badge::after` в `css/core.css`;
3. значение мета-маркера `rp-cabinet-architecture` в `index.html`;
4. номер версии в этой документации и `QUICK_GUIDE.txt`.

Это обязательный пункт: номер внутри нижней плашки не должен оставаться от старой сборки.

## Проверка

- синтаксис всех JS;
- конфликт «ник на ПК / галочка на телефоне»;
- обновление страницы телефона без сброса профиля;
- сохранение даты регистрации;
- отдельные ступени и прогресс Academy, MA, USAF, MP, DF, SD и ED;
- обязательный скриншот только для участия в СО и ГМП;
- очередь подтверждений после отметки задания;
- оригинальный размер изображения;
- формирование, открытие и ручное удаление отчёта;
- автоматическая очистка через 8 дней;
- мобильная ширина 360 px без пересечения ника и аватара.
